# How it reads each agent

Three facts shape everything here, and each one was settled by measurement rather than by argument.

## 1. A quota read must cost nothing

A monitor that spends quota in order to display quota is self-defeating, and the failure would be invisible — a few hundred tokens per poll is a real bite out of a five-hour window, and no UI would say so.

Measured on 2026-09-17: twelve account reads on one connection, and the lifetime token counter did not move.

| | before | after |
|---|---|---|
| Lifetime tokens | 318,009,023 | 318,009,023 |
| Percentages used | 33% / 13% | 33% / 13% |
| Session files on disk | 231 | 231 |

The positive control is the half that makes that zero mean something: the same counter moved by **+29,188,602** across a day of ordinary use. A counter that cannot move looks exactly like a counter that did not.

Claude Code's route is the same shape: an account read, made with the sign-in Claude Code keeps on your Mac. It is the request Claude Code's own `/usage` makes, and no model is in the loop.

**What is not allowed in, and would look perfectly reasonable:** asking an agent. A prompt along the lines of *"how much quota is left?"* is a model turn and costs tokens on every poll. It is the easiest route to build and the one Lancetta will never take.

## 2. Both can be asked — and Claude Code itself still cannot

They look symmetrical from the panel now, and the reason they can is worth knowing.

**Codex** answers an account question directly, over its own local interface. So it refreshes on the interval you set and again on **Refresh now**, and the reading is as current as the last poll. The same answer says how many free resets the account holds, at no extra cost; what each one is called and when it lapses is a second question, asked once when the count changes rather than on every poll.

**Claude Code** has no equivalent question of its own: no usage subcommand, no rate-limit block in its hooks, no quota figure in its metrics export. But its *account* does. The numbers Claude Code shows under `/usage` come from one account read, and Lancetta makes the same one, with the sign-in Claude Code keeps on your Mac. So Claude refreshes on the same interval and on **Refresh now** — once you have connected it, which is one click and one macOS dialog. [Getting Started](/docs/getting-started#claude-code) says exactly what that click does and does not do.

Until then, or if you would rather not hand the app a keychain item, the older route still works: a line in your status-line script writes the numbers to a file, and Lancetta reads the file. That reading is only as fresh as your last rendered session, and the card says so instead of pretending to be live — and offers Connect right there, because a file that exists outranks the offer, and a Mac wired that way was otherwise never shown it.

## A window one model keeps to itself

Some plans give **one model its own weekly limit**, counted separately from everything else. It can run out while the percentage on your menu bar still reads two thirds — and until Lancetta 0.6 nothing here drew it, because the two windows every monitor reads are not the whole answer.

They are not the whole answer literally: the account's reply carries a **row per meter**, each one saying what kind it is, how much of it is spent, when it resets, and — where a row belongs to one model — that model's name. Lancetta reads every row it is sent and draws the ones with a name, under the name the account gave them. Nothing here has a list of models in it, so a window that appears tomorrow for a model nobody has heard of yet appears on the card the same day.

A spent window of this kind is **not** an agent with nothing left, and Lancetta does not say it is: your agent carries on with another model, the menu bar keeps drawing the windows that belong to everything, and what you get instead is one sentence naming the model and the day it comes back. See [Alerts](/docs/alerts).

**This is an account-route fact.** The status-line payload carries the two general windows and nothing else, so a Claude card reading that file cannot see these rows at all — one more thing [Connect](/docs/getting-started#claude-code) buys, and the card says so.

## The other route

Before 0.3 the only way in was a file: Claude Code hands its status-line command a payload that carries the same two windows, and one line in that script writes them where Lancetta can read them. It still works, and it is the route for anyone who would rather not hand the app a keychain item.

```sh
# in your status-line script, immediately after you read stdin:
mkdir -p ~/.cache/claude-statusline
printf '%s' "$input" | /usr/bin/jq -c \
  '{rate_limits, observed_at: (now | todate)}' \
  > ~/.cache/claude-statusline/claude-limits.json
```

Two things about it, because Lancetta shows both rather than hiding them:

- **The card is only as fresh as your last rendered session.** If nothing has rendered a status line for two hours, the reading is two hours old, and the panel says so.
- **The file is a shared slot.** Every Claude Code session that renders writes it, so two sessions can disagree. Lancetta prefers a complete older reading over a fresher partial one.

With the account connected, the file is not read at all.

## The history, and why the two series are not the same kind of number

Alongside the rate limits, Codex keeps **the whole token history** and gives it away on the same free route: a lifetime total, the best single day, the streaks, and one bucket per day that was used. Measured on 2026-09-17: 46 buckets across a 163-day span, and the buckets **sum to the lifetime total exactly** — so it is the complete series rather than a window onto it.

**Claude Code publishes no counterpart at all.** Its payload is two percentages and two reset instants. There is no history in it, anywhere.

So Claude's half of [the window's chart](/docs/the-window#usage) is not published, it is **reconstructed** — from Claude Code's own transcripts on this Mac, which carry a token count on every assistant message. That buys a real series and costs two things the caption states rather than hides: sessions run on another machine are not in it, and **cache reads are left out**, because they re-send the same context every turn and were 98% of one day's total (762 M of 774 M). Leaving them in would put Claude's line an order of magnitude above Codex's and mean nothing. The chart names each series, so neither is ever drawn under the other's name.

Two properties of that series shape how it is drawn:

- **It is sparse.** Only days with usage appear — 46 entries across 163 days. Plotting the buckets in the order they arrive turns five months into a month and a half, so the quiet days are filled back in. They are drawn as gaps, never as zeroes.
- **It lags by hours, not by a day.** On one afternoon the newest bucket was still yesterday's; by that evening the current day had appeared. The caption under the chart says which of those two states you are looking at rather than asserting one.

The history is not on the poll timer. It is a second round trip and it only changes once a day, so it is read when the window opens and when you ask for it.

## 3. An unknown is never a number

`0%` is a reading. *Unknown* is the absence of one. Conflating them is what produced a status line saying a healthy account was empty, so in Lancetta the two are different things all the way down: the value that carries a percentage has no numeric default, and the timestamp on a reading is not optional.

## The plan, and where it comes from

The plan on each card is read from the account, not typed into a setting. For Claude Code there is a field nearby that *looks* like a second quota feed and is not — when this was checked it was 14.8 days stale with every window at zero. Lancetta does not read it, and neither should anything else.
